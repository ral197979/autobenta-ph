## Platform: Render.com

AutoBentaPH is deployed on Render.com as a single web service serving both the Express API and the React frontend (frontend compiled into `backend/public/` at build time).

| Property | Value |
|---|---|
| Platform | Render.com |
| Runtime | Node.js |
| Deploy trigger | Automatic on git push to `main` |
| Health check | `GET /api/health` |
| Database | Render managed PostgreSQL 16 |
| Build config | `render.yaml` (checked into repo) |

Infrastructure-as-code via `render.yaml` means the deployment configuration is version-controlled and reproducible. No manual dashboard configuration is required for a new environment.

## render.yaml Summary

`render.yaml` defines two resources:

**Database:**
- Engine: PostgreSQL 16
- Plan: Starter (configurable)
- Name: `autobenta-db`

**Web service:**
- Runtime: Node
- Build command: see Build Pipeline section
- Start command: `npx prisma migrate deploy && node src/server.js`
- Health check path: `/api/health`
- Auto-deploy: enabled on push to `main`

**Env vars defined in render.yaml** (non-secret):

| Variable | Value | Notes |
|---|---|---|
| `NODE_ENV` | `production` | Enables production mode |
| `PORT` | `10000` | Render internal port |
| `FRONTEND_URL` | (set per env) | Required for CORS |

**Env vars set in Render dashboard** (secrets, not in render.yaml):

| Variable | Required | Notes |
|---|---|---|
| `DATABASE_URL` | Yes | Auto-injected from linked DB |
| `JWT_SECRET` | Yes | Auto-generated by Render |

| `V8ATLAS_WEBHOOK_SECRET` | If enabled | HMAC verification |

## Build Pipeline

The build runs in 5 sequential steps on every deploy:

| Step | Command | Purpose |
|---|---|---|
| 1 | `npm install` | Install all dependencies (root + workspaces) |
| 2 | `cd frontend && npm run build` | Vite compiles React app to `frontend/dist/` |
| 3 | `cp -r frontend/dist backend/public` | Copies compiled frontend to Express static serving path |
| 4 | `cd backend && npx prisma generate` | Generates Prisma client from schema |
| 5 (start) | `npx prisma migrate deploy && node src/server.js` | Applies pending migrations, starts server |

**Critical:** Steps 2 and 3 mean the frontend is compiled at deploy time and baked into the backend container. There is no separate frontend service or CDN required — Express serves the compiled React app from `backend/public/`.

## Migration Safety

`npx prisma migrate deploy` runs automatically on every deploy before the server starts.

**Safety properties:**
- **Idempotent:** already-applied migrations are skipped (tracked in `_prisma_migrations` table)
- **Ordered:** migrations apply in chronological order
- **Non-destructive by convention:** migration files are append-only in git; destructive changes require explicit `DROP`/`ALTER` in migration SQL
- **Failure behavior:** if `migrate deploy` fails, the process exits non-zero; Render marks the deploy as failed and does not switch traffic

**Migration files location:** `backend/prisma/migrations/` — tracked in git alongside schema changes.

**Warning:** `migrate deploy` does not run `migrate dev` (which generates new migrations). Only pre-committed migration files are applied in production. Never run `prisma migrate dev` in a production environment.

## Dockerfile

**Location:** `Dockerfile` (repo root)

Multi-stage build to minimize final image size and separate build-time from runtime dependencies:

**Stage 1 — Frontend build** (`node:20-alpine`):
```dockerfile
FROM node:20-alpine AS frontend-build
WORKDIR /app/frontend
COPY frontend/package*.json ./
RUN npm ci
COPY frontend/ ./
RUN npm run build
```

**Stage 2 — Backend runtime** (`node:20-alpine`):
```dockerfile
FROM node:20-alpine AS backend
WORKDIR /app/backend
COPY backend/package*.json ./
RUN npm ci --omit=dev
COPY backend/ ./
COPY --from=frontend-build /app/frontend/dist ./public
RUN npx prisma generate
HEALTHCHECK --interval=30s --timeout=10s --start-period=60s \
  CMD wget -qO- http://localhost:$PORT/api/health || exit 1
CMD ["sh", "-c", "npx prisma migrate deploy && node src/server.js"]
```

**Key decisions:**
- `--omit=dev` in stage 2 excludes devDependencies from the production image
- `HEALTHCHECK` instruction allows Docker/Render to detect unhealthy containers
- Frontend `dist/` is copied from stage 1 — no Node.js frontend runtime in production image
- `prisma generate` runs at build time; `migrate deploy` runs at container start

## docker-compose.yml

**Location:** `docker-compose.yml` (repo root)

Provides a local development environment that mirrors production:

```yaml
services:
  app:
    build: .
    ports: ["3000:10000"]
    environment:
      DATABASE_URL: postgresql://autobenta:autobenta@postgres:5432/autobenta
    depends_on: [postgres]
    volumes:
      - ./uploads:/app/backend/uploads

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_USER: autobenta
      POSTGRES_PASSWORD: autobenta
      POSTGRES_DB: autobenta
    volumes:
      - postgres_data:/var/lib/postgresql/data
```

**Usage:**
```bash
docker-compose up          # Start app + database
docker-compose down -v     # Stop and remove volumes (clean slate)
```

## .env.example

**Location:** `.env.example` (repo root)

Documents every environment variable the application reads, with required/optional classification and example values. Used to onboard new developers and as a checklist when configuring a new Render environment.

All variables are classified as:
- `REQUIRED` — application will not start without this (process.exit(1))
- `OPTIONAL` — has a safe default or is feature-gated

The file contains no real credentials and is safe to commit to the repository.

## Required Env Vars (Startup Validation)

The following variables are validated at server startup. If any are missing, the process exits with code 1 and logs a clear error message:

| Variable | Validation | Consequence if missing |
|---|---|---|
| `DATABASE_URL` | Must be set | Server exits — no DB, no service |
| `JWT_SECRET` | Must be set | Server exits — cannot issue auth tokens |
| `FRONTEND_URL` | Must be set | Server exits — CORS would block all browser requests |

This fail-fast behavior prevents the server from starting in a misconfigured state that would appear healthy but fail on first real request.

## Rollback Procedure

**Standard rollback (no schema changes):**
1. Render Dashboard → Web Service → Deploys tab
2. Find the last known good deploy
3. Click Rollback — Render re-runs the previous build artifact immediately
4. No data loss; no database changes required

**Rollback with schema changes:**

If the failed deploy included a migration, the database schema is already updated. Rolling back the code without rolling back the schema will cause runtime errors if the old code references dropped columns or missing tables.

Procedure:
1. Identify what the migration changed
2. If additive (new table, new column with default): safe to roll back code; old code ignores the new schema elements
3. If destructive (dropped column, renamed column): must restore database from backup before rolling back code
4. Run: `./scripts/restore.sh <last-good-backup> $DATABASE_URL`
5. Then roll back code in Render dashboard

**Prevention:** mark destructive migrations clearly in commit messages. Run `prisma migrate status` before deploying to confirm what will be applied.

## Zero-Downtime Deploys

Render performs rolling deploys:
1. New container is built and started
2. Health check (`GET /api/health`) must return HTTP 2xx within the configured timeout
3. Once healthy, traffic switches to the new container
4. Old container is terminated

**Result:** if the new deploy fails the health check, Render keeps the old container running and marks the deploy as failed. Users experience no downtime.

**Requirement:** `GET /api/health` must return HTTP 200 within 60 seconds of container start (Render default). The current implementation queries the database and all subsystems — if the database is not reachable at start, the health check returns HTTP 503 and the deploy fails. This is the correct behavior.

## Secrets Management

| Secret | How managed |
|---|---|
| `JWT_SECRET` | Auto-generated by Render on first deploy; stored in Render env vars |
| `DATABASE_URL` | Auto-injected by Render from the linked PostgreSQL service |
| `V8ATLAS_API_KEY` | Set manually in Render env vars; never in `render.yaml` or git |
| `V8ATLAS_WEBHOOK_SECRET` | Set manually in Render env vars; never in `render.yaml` or git |

**Rules:**
- Secrets never appear in `render.yaml`, `.env.example`, or any committed file
- `.env` is in `.gitignore`
- `render.yaml` only contains non-secret configuration (ports, build commands, public env vars)
